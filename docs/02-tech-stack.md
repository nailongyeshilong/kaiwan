# 02 - 技术架构（Tech Stack）

> 项目：开玩（KaiPlay）
> 文档版本：V1.0

---

# 1. 文档目的

本文档定义《开玩》项目的技术架构、开发框架及第三方依赖。

本文档回答以下问题：

* 项目使用哪些技术？
* 为什么选择这些技术？
* 各技术组件承担什么职责？
* 各层之间如何协作？

---

# 2. 项目定位

《开玩》属于本地离线移动应用（Offline First）。

产品特点：

* 无用户登录
* 无服务端
* 无云同步
* 本地数据存储
* 中小型项目
* UI 与动画体验优先
* 后续具备云端扩展能力

---

当前支持平台：

* Android
* iOS

* Web
* Windows
* macOS
* Linux

# 5. 整体架构

项目采用：

**Feature First + MVVM + Repository Pattern**

整体架构如下：

```text
Presentation（UI）
        │
        ▼
State（Riverpod）
        │
        ▼
Repository
        │
        ▼
Local Database（Hive）
```

业务数据始终沿单一方向流动。

任何模块不得跨层直接访问。

---

# 6. 技术选型

## Flutter

作为整个项目开发框架。

负责：

* 页面渲染
* 动画
* 手势
* 跨平台能力

---

## Riverpod

作为统一状态管理方案。

负责：

* 页面状态
* 生命周期
* 数据刷新
* Provider 管理

项目中所有页面状态均由 Riverpod 管理。

---

## GoRouter

作为统一路由管理。

负责：

* 页面跳转
* 路由参数
* 深链接扩展（预留）

所有页面均通过 GoRouter 管理。

---

## Hive CE

作为本地数据库。

负责保存：

* 游戏库
* 游玩记录
* 应用设置
* 每日抽取状态

选择 Hive 的原因：

* 轻量
* 性能高
* API 简单
* 非关系型数据更符合当前项目
* 无需 SQL

---

## Image Picker

负责：

从系统相册选择图片。

仅负责图片选择，不负责图片存储。

---

## Path Provider

负责：

获取应用沙盒目录。

所有游戏图片均复制至应用沙盒后保存。

---

## Logger

负责：

统一日志输出。

便于开发调试。

---

## UUID

负责：

生成业务对象唯一 ID。

包括：

* Game
* PlayHistory

---

## intl（预留）

当前版本默认中文。

提前预留国际化能力。

---

# 7. 数据存储策略

所有业务数据均保存在本地。

包括：

* 游戏信息
* 图片路径
* 游玩记录
* 每日抽取状态
* 设置

图片文件保存在应用沙盒。

数据库仅保存图片路径。

---

# 8. 数据访问方式

项目统一采用 Repository Pattern。

所有数据访问流程如下：

```text
UI

↓

Provider

↓

Repository

↓

Hive
```

UI 不直接访问数据库。

Repository 是唯一的数据访问入口。

未来如切换 SQLite 或云数据库，不影响上层业务。

---

# 9. 状态管理策略

采用响应式状态管理。

页面状态由 Riverpod Provider 管理。

Repository 负责业务数据。

UI 仅负责展示。

三者职责保持独立。

---

# 10. 动画策略

所有复杂动画均使用 Flutter 原生动画体系实现。

首页抽卡动画采用多个独立阶段组合：

1. 卡片滚动
2. 卡片停止
3. 卡片翻转
4. 展示结果

各阶段可独立维护和扩展。

---

# 11. 主题策略

项目统一使用 Flutter Theme。

颜色、字体、圆角等设计资源统一由 Theme 管理。

具体设计规范见：

《04-design-system.md》

---

# 12. 网络策略

V1.0 不涉及任何网络接口。

应用所有功能均可离线运行。

后续若增加：

* Steam 导入
* 云同步
* AI 推荐

统一采用 Dio 接入。

---

# 13. 扩展能力

当前架构支持未来增加：

* 登录系统
* 云同步
* Steam 游戏导入
* AI 推荐
* 游戏标签
* 多主题
* 多语言
* 成就系统

新增功能无需调整整体架构。

---

# 14. 技术原则

整个项目遵循以下原则：

* Offline First
* Feature First
* MVVM
* Repository Pattern
* 单向数据流
* 响应式状态管理
* 高内聚、低耦合
* 易于维护
* 易于扩展
